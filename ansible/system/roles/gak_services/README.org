#+TITLE: gak's general services
#+options: toc:nil num:nil

Gak's private application stack: Koito for listening history and Nextcloud for
calendar, DAV and the other groupware and file features that can be enabled as
they become useful. Guix System declares the rootless podman containers and GNU
Shepherd lifecycle; Ansible declares their state, secrets and operator commands.

This file is documentation, not a source. Nothing tangles out of it; the role
beside it is the source of truth. It records the reasoning that the
configuration cannot state on its own.

* Where the container is declared

Not here. gak runs GNU Shepherd and has no systemd at all, so a =.service= unit
under =~/.config/systemd/user= is a file nothing reads. The containers are
declared in =guix_config='s =system.scm=, and the values they need — uid, gid,
timezone, ports, image version — are host facts in =host_vars/gak/main=, shared
between that template and this role.

This role owns only what the containers read and write.

A Guix Home Shepherd service would have been the smaller change, but Guix Home
starts the user Shepherd from =~/.guix-home/on-first-login=: after a power cut,
nothing would come up until someone logged in. System Shepherd services start at
boot.

** Why not oci-service-type directly

=system.scm= builds the services by calling =oci-configuration->shepherd-services=
rather than by adding =oci-service-type= to its service list.

That service type also extends =account-service-type= with a =user-account= for
whatever its =user= field names. lobo already has an account, and =/etc/passwd=
is written from that list without deduplication, so the result is two lobo
records — the second in group =users= with =/sbin/nologin=. Guix only warns.
Calling the builder takes the Shepherd services and leaves the account alone;
=rootless-podman-service-type= already covers the rest of what the service type
would have contributed, namely podman in the system profile and lobo's subuid
and subgid ranges.

** Why it starts without a login

Rootless podman puts its runroot under =/run/user/1000=, which lobo cannot
create. elogind creates it at boot because lobo is a lingering user. That is
host state rather than configuration, set once:

#+begin_src sh
sudo loginctl enable-linger lobo
#+end_src

Without it the containers fail at boot with =RunRoot is pointing to a path which
is not writable=.

* Why not ListenBrainz itself

The obvious reading of "a private ListenBrainz" is to run the ListenBrainz
server. That was investigated and rejected.

MetaBrainz publishes no supported production deployment. =docker/docker-compose.yml=
in the server repository is a development environment: it bind-mounts the source
tree into the containers and builds the application image locally. A minimum
viable instance is eight containers — web, api_compat, timescale_writer,
background_tasks, websockets, TimescaleDB, Redis and RabbitMQ — and signing in
requires registering an OAuth application on musicbrainz.org, so authentication
depends on MetaBrainz even though the listens do not.

That instance still cannot resolve a scrobble to a MusicBrainz recording. There
is no small mapping dataset to fetch periodically: MetaBrainz generates the
mapping tables from their own MusicBrainz database replica, and reaching feature
parity means running that replica, Typesense and =mbid_mapper= as well. For a
single user's listening history, the mapping infrastructure would be by a wide
margin the largest thing on the machine.

Koito reaches the same goal from the other end. It speaks the ListenBrainz
submission API, so every scrobbler that can be pointed at a custom ListenBrainz
URL works unchanged, and it resolves loose metadata by querying the *public*
MusicBrainz API at request time rather than from a replica. One Go binary, one
SQLite file. If a local mirror ever exists here, =KOITO_MUSICBRAINZ_URL= points
it at that instead.

* Secrets

Nothing secret may go into =system.scm=. That file is built into =/gnu/store=,
which is world-readable, so a password written there is published to every user
on the machine.

Koito reads any setting from a file when the variable is given a =_FILE= suffix.
The role writes the admin password to =~/services/koito/secrets/default-password=
at 0600 and =system.scm= names only the path.

That password seeds the first account and is read only while the database is
empty. Changing it in the web UI afterwards leaves the vault stale; update
=koito_admin_password= in =host_vars/gak/vault= to match, or a rebuilt instance
will disagree with the one that already exists.

* Driving it

#+begin_src sh
sudo herd status koito
sudo herd restart koito
#+end_src

* Nextcloud

The Nextcloud stack uses four containers on its own =nextcloud_net= network:

- =nextcloud= is the Apache frontend, bound only to =127.0.0.1:8080=.
- =nextcloud-db= is PostgreSQL and has no host port.
- =nextcloud-redis= provides memory cache and transactional file locking and
  has no host port.
- =nextcloud-cron= runs the upstream five-minute background-work loop against
  the same application tree.

The community =nextcloud:apache= image is used rather than Nextcloud AIO. AIO
expects to create and supervise child containers through a container socket;
that duplicates the ownership Guix and Shepherd already provide here. The
application, PostgreSQL and Redis images are pinned by release and manifest
digest in =host_vars/gak/main=.

Primary state is under =~/services/nextcloud= on the NVMe:

- =html= contains the application, configuration, installed apps and user data.
- =postgres= contains the database cluster.
- =secrets= contains the database, Redis, account and Restic credentials.
- =backup-staging= holds a database dump only while a backup is running.

The initial =nextcloud-admin= account is reserved for administration. Daily
clients use the separate =lobo= account. Ansible creates that account after the
containers are running, installs Calendar, selects cron background jobs, and
sets the Brazilian phone-region default:

#+begin_src sh
ansible-playbook gak.yaml --tags gak-services-bootstrap
#+end_src

The bootstrap is idempotent. The daily password is kept in the encrypted Gak
vault and deployed in a private environment file. =podman exec --env-file=
loads it only for account creation; it is not part of the long-running
container environment.

The secret directory is not listable by application processes. Its mapped
=www-data= group may traverse it and read only =redis-password=, which the
upstream PHP Redis configuration loads for both web requests and cron. The
Redis process receives its group-readable configuration through an individual
read-only bind mount. The remaining credentials stay readable only by root in
the container namespace.

** Applying and inspecting the stack

Ship the Ansible-owned files, build the generated Guix expression, then apply
it while watching the host:

#+begin_src sh
ansible-playbook gak.yaml --tags guix,gak-services
ssh gak guix system build ~/.config/guix/system.scm
ssh -t gak sudo guix system reconfigure ~/.config/guix/system.scm
#+end_src

Then inspect the actual services and their isolated listener:

#+begin_src sh
sudo herd status nextcloud nextcloud-db nextcloud-redis nextcloud-cron mcron
podman ps -a
podman network inspect nextcloud_net
ss -ltnp | grep 127.0.0.1:8080
podman exec --user 33 nextcloud php occ status
podman exec --user 33 nextcloud php occ setupchecks
#+end_src

** Calendar clients

The canonical origin is the named Nextcloud Service URL derived from the
private =gak_tailnet_dns_suffix= vault value. Log in as =lobo=, not
=nextcloud-admin=. Calendar clients that ask for a DAV server can discover
collections by appending this path to that origin:

#+begin_example
/remote.php/dav
#+end_example

On Android, DAVx⁵ can use its Nextcloud login flow and then exposes calendars
to the system calendar database; any calendar application can render them. The
Nextcloud Android app is useful for files and sharing but does not replace the
DAV calendar adapter. Desktop clients can use the same CalDAV discovery URL.

** Backup and restore

At 03:30 local time, system mcron runs =~/.local/bin/gak-nextcloud-backup= as
=lobo=. The command prevents overlap, initializes an encrypted Restic
repository when needed, enters maintenance mode, creates a native PostgreSQL
dump, snapshots that dump with the complete =html= tree, clears maintenance
mode even after failure, applies retention, prunes, and checks the repository.
Restic runs inside podman's user namespace so it can read files owned by the
container's mapped =www-data= identity without relaxing their host permissions.

The repository is =/marak/backups/nextcloud/restic= on a physical disk separate
from the NVMe primary state. Retention keeps seven daily, five weekly and twelve
monthly snapshots. This protects against local state loss and mistakes; it is
not an off-site copy and does not protect against loss of both disks or the
host.

Run the caller-visible recovery gate after first deployment and before an
upgrade:

#+begin_src sh
gak-nextcloud-backup
gak-nextcloud-restore-check
#+end_src

The restore check decrypts the latest snapshot into a private scratch
directory, verifies the application/data markers, restores the dump into an
ephemeral isolated PostgreSQL container, requires real application tables, and
removes the scratch state. A full recovery uses the same snapshot, restores
=html= to an empty bind-mount root, initializes an empty PostgreSQL cluster, and
applies the database dump before starting the application containers.

Redis contains rebuildable cache and lock state and is deliberately excluded
from backup.

* Pointing a scrobbler at Koito

Koito listens only on gak's loopback interface. Its named Tailscale Service
terminates HTTPS and proxies to that listener, so in Pano Scrobbler choose
*Custom ListenBrainz*, append =/apis/listenbrainz/= to the named Koito Service
origin, and use the API token from Koito's own settings page. Any client that
accepts a custom ListenBrainz URL — Navidrome, Music Assistant,
web-scrobbler — configures the same way.

Koito can also relay what it receives on to another ListenBrainz-compatible
server, so running it alongside an existing setup rather than in place of one is
a configuration change, not a migration.

* Reaching it from outside the house

Through Tailscale, added to gak in =system.scm=. No port is forwarded and
nothing is exposed to the internet.

Guix upstream packages Tailscale's Go dependencies but not Tailscale itself, so
=tailscaled= and =tailscale-service-type= come from the rosenthal channel, which
=channels.scm= already lists for other reasons.

Rosenthal's service remains the integration point, but the Tailscale package is
overridden in the local =11xx= channel. Tailscale Serve has had remotely
reachable security defects, so waiting for a secondary channel to publish a
fixed client is not an acceptable update path. The override pins a reviewed
release and its source and vendor hashes; bump it deliberately when the admin
console or Tailscale's security bulletins require a newer version.

** Authenticating the machine

Tailscale requires an account, created at https://login.tailscale.com/start.

It is deliberately not an identity provider and has no passwords of its own, so
there is *no e-mail or magic-link sign-up*. The only options are Google,
Microsoft, GitHub, Apple, and custom OIDC. Passkeys exist, but for
authenticating to a tailnet already joined — not for creating the account. The
free Personal tier covers up to six users and unlimited devices.

The choice is stickier than the sign-up page suggests, and worth making once:

- A tailnet cannot be migrated *to or from* GitHub or Apple at all.
- One created from a Gmail address is a "shared domain" tailnet and can change
  provider only through Tailscale support.
- Custom OIDC is the escape hatch, but it wants a domain of its own and
  WebFinger configuration.

Whichever identity is used becomes the root of trust for every device on the
tailnet, so it wants a passkey or hardware key on it and real recovery options.
A seldom-used account is the wrong choice here for a reason that has nothing to
do with security: Google deletes accounts left inactive for two years, and it
would take tailnet ownership with it.

The daemon runs with no identity until it is authenticated once by hand:

#+begin_src sh
sudo tailscale up
#+end_src

That prints a URL. It is a one-time registration nonce bound to this machine's
public key: it authorises exactly one pending node and is then spent. It is not
a standing credential, and it is not what secures the machine afterwards.

** What secures it afterwards

- The *node key* under =/var/lib/tailscale=, generated here and never sent
  anywhere. That is the credential from then on.
- The *admin console*, which is the control point. Every machine is listed;
  removing or disabling one cuts it off immediately.
- *Key expiry*, 180 days by default, after which the node must re-authenticate.
  For a headless server that is a scheduled outage nobody will remember the
  cause of — turn expiry off on gak's row.
- *ACLs*, which decide who may reach what. A personal tailnet defaults to
  every device reaching every other device.
- *Device approval*, optional, which holds a newly added machine pending until
  it is approved by hand.

An *admin* is a user account role, not a device that happens to be logged in.
The first user is normally the sole *Owner*, which includes every admin
permission. Owners, Admins and IT admins can approve devices. A new device can
authenticate as an ordinary member and still remain unable to send or receive
tailnet traffic until one of those roles approves it in the admin console.

** What Tailscale can and cannot see

The coordination server is a drop box for *public* keys plus metadata about
where each node currently is. Each node generates its own WireGuard keypair
locally and the private half never leaves it, so only the two endpoints can
encrypt or decrypt. Tailscale carries no user traffic and cannot read it. When
two nodes cannot connect directly the traffic falls back through Tailscale's
DERP relays, still encrypted end to end.

The residual risk is authorisation, not confidentiality: the control plane
distributes the key list, so a compromised one could hand these nodes a key for
a machine that was never approved. *Tailnet lock* closes that — existing
devices sign new ones, so the control plane cannot inject a node on its own.

If that trust is unwanted altogether, *Headscale* is an open-source
reimplementation of the coordination server that can be self-hosted, using the
same clients.

** Tagged host and named Tailscale Services

The stable service identities are =svc:koito= and =svc:nextcloud=. Named
Services require a tag-based host. The tailnet policy must first make
=autogroup:admin= the owner of =tag:server= and grant the intended members
access to the tagged host's SSH port and both Services' HTTPS port. Apply the
policy before changing Gak's identity; tagging removes its user ownership.

Request the tag and verify SSH from another node before touching ingress:

#+begin_src sh
sudo tailscale up --advertise-tags=tag:server
tailscale status
ssh gak true
#+end_src

Then reconcile both service handlers and approve their advertisements in the
Tailscale admin console:

#+begin_src sh
gak-tailscale-services
sudo tailscale serve get-config --all -
#+end_src

Only after both named Service origins work from another tailnet node should the
legacy node handler be removed with =sudo tailscale serve reset=. Re-run the
named-service command and inspect =tailscale serve status --json= afterwards;
the reset operates on node Serve state, while the named configurations remain
separate.

Named Serve configuration lives in tailscaled's state and resumes after a
reboot or a =tailscale down= / =tailscale up=. It is private to the tailnet;
=tailscale funnel= is the distinct command that publishes a service to the
internet and is not used here.

Serve obtains and renews a public certificate from Let's Encrypt. Tailscale
answers the DNS-01 validation challenge for the private service name, while the
certificate private key and ACME account key stay on gak. This is not a private
Tailscale certificate authority.

Like every publicly trusted web certificate, the certificate is recorded in
append-only Certificate Transparency logs. Those logs let certificate
authorities, browsers and observers detect mistaken or malicious issuance; they
also reveal the exact service names. They reveal neither the service contents
nor a route around Tailscale. The names are public, but the addresses remain
reachable only by peers allowed into this tailnet. For that reason the concrete
tailnet suffix belongs in the encrypted vault, not this publishable document.

The backend port is published as =127.0.0.1:4110= rather than =0.0.0.0:4110=.
That makes Serve the only network path to Koito: LAN clients cannot bypass its
tailnet access controls or forge the identity headers Serve adds.

** Updating Tailscale

Tailscale publishes a stable client about every four weeks and additional patch
releases when needed. Do not chase release candidates or the odd-numbered
unstable track. Review the stable changelog monthly; subscribe to the security
bulletin RSS feed and handle those releases immediately.

An update changes two fixed-output hashes in
=11xx/packages/networking.scm=. Obtain the source hash from a checkout of the
new stable tag:

#+begin_src sh
git clone --depth=1 --branch vVERSION https://github.com/tailscale/tailscale
guix hash -rx tailscale
#+end_src

Set the vendor hash temporarily to 52 zeroes and build the package on gak. The
fixed-output mismatch prints the correct vendor hash; replace the zeroes with
it and build again:

#+begin_src sh
guix build -L ~/11xx-guix-channel \
  -e '(@ (11xx packages networking) tailscale)' --no-grafts
#+end_src

Run the built =bin/tailscale version= as part of the package gate. Rosenthal's
build flags stamp its package version into the binaries, so an override must
replace those flags as well as its source and vendor hashes.

Deploy both the package and system expression, commit the local channel, update
the Guix profile, and reconfigure. The running node key, Serve configuration and
certificate state remain under =/var/lib/tailscale= and survive the package
replacement.

* Version pinning

=gak_koito_version= is an explicit tag, not =latest=. Koito is young enough for
that to matter: it replaced PostgreSQL with SQLite outright between v0.1.10 and
v0.2.1, migrating data on the way. Bumping the pin is a deliberate act — read
the release notes first, and take a copy of =~/services/koito= before
reconfiguring.

Nextcloud, PostgreSQL and Redis are pinned to a release tag and manifest digest.
Changing a digest without changing the documented tag is appropriate only for
an upstream base-image rebuild that has been reviewed. Before any application
or database upgrade, run the backup and restore check, read the supported
upgrade path, build the generated system expression, and verify the running
image plus =occ status= after reconfiguration.

Koito's SQLite history is not yet included in the Nextcloud backup command; it
remains a separate, small follow-up recovery surface.
